# Business Object: Diagram

## Definition

A `Diagram` is a stored graphical view of a part of the architecture repository: an instance of a [Viewpoint](./viewpoint.md) that places entities and connections on a canvas with position and size, plus elements that belong only to the diagram, such as [sticky notes](./diagram-note.md).

## Description

The viewpoint defines *what may* appear and *how* it is drawn; the diagram is *one concrete drawing* – for example "Application Cooperation View – current" or "CRM migration target state". The diagram does not own the entities it shows: removing a shape from a diagram leaves the entity in the repository, and an entity can appear in many diagrams. What the diagram owns is its **layout** (positions, sizes, bend points, z-order) and its **diagram-only elements** (sticky notes, groups without semantics).

Diagrams are edited by several people at the same time (§21.10): their working state is merged automatically and turned into versions of the diagram layout and of the entities and connections changed through it. Comment threads ([CommentThread](./comment-thread.md)) discuss a diagram without being part of it.

Until this object was modeled, the [TreeNode](./tree-node.md) referred to diagrams as a "future BO"; the canvas requirements (REQ-040, REQ-063, REQ-072) describe its editing.

## Versions and Checkpoints

Continuous co-editing is recorded on two levels ([ADR-047](../adrs/ADR-047-real-time-collaboration.md), owner decision of 2026-10-28):

- **Operation log**: every operation the server accepts, in server order, with author, time, element, attribute and old and new value. A gesture is one operation (a drag records the final position). It serves resynchronisation after reconnects and point-in-time reconstruction; each operation is also recorded in the audit trail.
- **Versions**: a version groups the operations of one author on the diagram. It closes after 2 minutes without a further operation of that author, after 15 minutes at the latest, or when the author leaves the diagram or loses the connection (defaults, configurable by the administrator). Entities and connections changed through the diagram get their own versions with the same rule.
- **Checkpoints**: named states of the whole diagram; restoring a version or checkpoint sets the whole diagram to that state.

## Lifecycle

```text
active → deleted (soft delete, restorable)
```

- `active`: visible and editable for persons with the permissions of the viewpoint's entity types
- `deleted`: hidden and not readable (404); it is neither listed nor counted, its name is free again and its entries in the navigation tree are left out; its notes and comment threads are hidden with it; shown entities are not affected. A person with `entity:restore` lists the deleted diagrams and restores one (`deleted → active`, version + 1); the restore is refused when a diagram that is not deleted has the name meanwhile.
- A diagram cannot exist without its viewpoint: deleting a viewpoint, or a package re-import that drops a system-defined one, removes its diagrams for good, the deleted ones included (change us-074-diagrams, owner decision 2026-11-19).

## Business Rules

| Rule ID | Statement | Trigger | Compliance Reference |
|---|---|---|---|
| BR-DG-01 | A shape of `kind = entity` MUST reference an entity whose type the viewpoint allows | onUpdate | – |
| BR-DG-02 | Removing a shape MUST NOT delete the entity; the shapes of a deleted entity MUST be hidden in all diagrams and MUST show again when the entity is restored | onUpdate, onEntityDelete, onEntityRestore | – |
| BR-DG-03 | Concurrent edits of the same diagram MUST be merged without losing any participant's change (REQ-199) | onUpdate | – |
| BR-DG-04 | A participant MUST NOT receive properties of shown entities that are hidden from them (property-level authorization, §21.8) | onRead, onCollaborate | REQ-126 |
| BR-DG-05 | A version MUST contain the operations of exactly one author; it closes after the configured idle time (default 2 minutes), the configured maximum duration (default 15 minutes) or when the author leaves or disconnects | onUpdate | REQ-199 |
| BR-DG-06 | Naming a checkpoint requires the permission to edit the diagram; a checkpoint is immutable except for its name and is recorded in the audit trail | onCreate, onUpdate | REQ-204 |
| BR-DG-07 | Creating and changing a diagram needs `entity:write`, reading it `entity:read`, restoring it `entity:restore`; service accounts with these permissions act like persons and are recorded as the actor; every change is audited (`diagram.created`, `diagram.updated`, `diagram.deleted`, `diagram.restored`, `diagram.layout-saved`) | onCreate, onUpdate, onDelete | ADR-032, ADR-033 |
| BR-DG-08 | The layout of a diagram MUST be saved as a whole in one atomic step with the version read (`If-Match`); entities created on the canvas get a name and a type only, are created with the checks and the audit of an entity write, and count as incomplete while a mandatory property of their type has no value (owner decision 2026-11-20) | onUpdate | ADR-033 |

## Examples

**Example 1**: Application cooperation view

```yaml
name: "Application Cooperation View – current"
viewpointId: archimate-application-cooperation
layout:
  shapes:
    - { shapeId: s1, kind: entity, entityId: crm-system, x: 120, y: 80, width: 160, height: 60, zIndex: 1 }
    - { shapeId: s2, kind: note, noteId: n1, x: 320, y: 40, width: 200, height: 120, zIndex: 2 }
  edges:
    - { edgeId: e1, connectionId: crm-to-erp, points: [] }
```

## Distinction from Similar Objects

- **NOT** [Viewpoint](./viewpoint.md): the viewpoint is the type (allowed elements, notation); the diagram is one drawing of that type
- **NOT** [Catalog](./catalog.md): a catalog is a tabular query, a diagram a drawn selection with layout
- **NOT** a rendered export (PNG, ArchiMate exchange file): exports are derived from the diagram

Modeled on 2026-10-28 because sticky notes and comment threads (UC-24) need an owner.
