# System Test Specification (Gherkin / BDD)

**V-model positioning:** These feature files are the system test specification,
created in parallel to the requirements phase. They define *what* is tested
— not *how*. The step definitions (Java code) are generated by Qwen 2.5 / Devstral
during the implementation phase.

**Generated:** 2026-06-30 from `requirements/req/REQ-*.md` via
`scripts/generate_feature_files.py`

## Tag Schema

```text
@functional         – Functional requirement
@non-functional     – Non-functional requirement
@performance        – Latency measurement / load test (always with @non-functional)
@compliance         – Compliance requirement (GDPR, WCAG)
@business-rule      – Business rule
@constraint         – Constraint

@must               – MoSCoW: MUST (mandatory for v1.0)
@should             – MoSCoW: SHOULD (high priority)
@could              – MoSCoW: COULD (optional)

@UC-01 … @UC-21     – Associated use case
@AC1 … @ACN         – Individual acceptance criterion

@skip               – Discarded requirement (e.g. REQ-021)
```

### Useful Filter Examples (Cucumber-CLI / Maven)

```bash
# Walking skeleton tests only (UC-06)
--tags "@UC-06"

# All auth tests (Must)
--tags "@functional and @must and (@UC-01 or @UC-02 or @UC-03)"

# Performance tests only
--tags "@performance"

# Everything except @skip
--tags "not @skip"

# Single AC
--tags "@AC2"
```

#### Headless Qwen2.5-14B Server (local, Mac Mini M1 16GB)

For generating the step definitions, Qwen 2.5 14B (4-bit quantization)
can be run locally as a headless LLM server — no GUI needed, addressed via
an OpenAI-compatible REST API.

```bash
# 1. Install Ollama
brew install ollama

# 2. Start as a background service (runs permanently on http://localhost:11434)
brew services start ollama

# 3. Pull the model (Q4_K_M = standard sweet spot quality/memory, approx. 8.5–9 GB)
ollama pull qwen2.5:14b-instruct-q4_K_M

# 4. Test request (OpenAI-compatible endpoint)
curl http://localhost:11434/v1/chat/completions -d '{
  "model": "qwen2.5:14b-instruct-q4_K_M",
  "messages": [{"role": "user", "content": "..."}]
}'
```

**Notes for 16GB unified memory (tight, but feasible):**

- Keep `num_ctx` small (e.g. 4096) — a larger context + 14B@Q4 exceeds 16GB
  and leads to swapping (very slow)
- Expected speed on M1 (not Pro/Max), 16GB: approx. 4–8 tokens/s —
  sufficient for overnight batch generation, not for interactive work
- Under memory pressure: `qwen2.5:14b-instruct-q3_K_M` (smaller, quality loss)
  or `qwen2.5:7b-instruct-q4_K_M` (considerably more comfortable on 16GB)
- Set `OLLAMA_HOST=0.0.0.0:11434` if access from another machine
  on the network (e.g. CI runner) is required
- `brew services start ollama` is enough for pure headless operation (LaunchAgent,
  no login required, starts at boot)

### 4. Run Regression Tests

```bash
# All tests
mvn test -Dcucumber.filter.tags="not @skip"

# Walking skeleton only
mvn test -Dcucumber.filter.tags="@UC-06 or @UC-01 or @UC-02"

# Performance only (requires Gatling plugin)
mvn test -Dcucumber.filter.tags="@performance"

# Quick smoke test (AC1 of each requirement)
mvn test -Dcucumber.filter.tags="@AC1 and @must"
```

## Regenerating Feature Files

```bash
cd /path/to/oea
python3 scripts/generate_feature_files.py
```

The script is idempotent — it overwrites existing feature files.
Manual changes to the `.feature` files are lost on regeneration;
therefore corrections should always be made in the source document (`requirements/req/REQ-*.md`).
