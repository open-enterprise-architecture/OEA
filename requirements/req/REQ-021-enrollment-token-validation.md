# REQ-021: Enrollment token validation and single use

## Statement

Before displaying the enrollment interface, the system MUST check whether the supplied enrollment token exists, has not yet been consumed, and has not expired; after successfully completed enrollment, the token MUST be marked as consumed and rejected on any renewed redemption.

## Rationale

The enrollment token is the only access control to the setup form for persons who are not yet logged in. Invalid or reused tokens would allow an attacker to register authentication methods for other people's accounts. Single use is a mandatory security prerequisite. Addresses UC-03 Basic Flow steps 2–3 and Exception Flow E1.

## Context

The token is generated by an administrator or a future invitation system (generation is not part of this requirement). UC-03 assumes that the token is cryptographically random and sufficiently long (≥ 128 bits of entropy). The link must be transmitted over HTTPS; to avoid exposing the token in server logs, it should be passed as a URL fragment (`#token=…`) so that it does not appear in the request log on the server side.

## Type-Specific Fields

### For type=functional

**Inputs**:
- Enrollment token (from the URL, e.g., as a query parameter or URL fragment)

**Processing**:
- Look up the token in the token database
- Check: exists? not consumed? not expired?
- On success: display the enrollment interface with the methods enabled for the instance
- After completed enrollment: set the token status to `consumed`, log the time of consumption

**Outputs**:
- Valid: enrollment form with available methods
- Invalid: generic error message ("Setup link invalid or expired"), no form

**Error Cases**:
- Token not found, already `consumed`, or expired → E1 from UC-03; no distinction between these cases in the externally visible error message (anti-enumeration)

## Acceptance Criteria

**AC1**:
- Given: a valid, unconsumed, unexpired enrollment token
- When: Kurt opens the setup link
- Then: the system shows the enrollment interface with the available methods

**AC2**:
- Given: an already consumed enrollment token
- When: Kurt opens the setup link again
- Then: the system shows a generic error message, no form

**AC3**:
- Given: an expired enrollment token
- When: Kurt opens the setup link
- Then: the system shows the same generic error message as in AC2 (no distinction)

**AC4**:
- Given: a successfully completed enrollment
- When: the token is to be redeemed again afterwards
- Then: it is rejected (identical to AC2)

**AC5**:
- Given: a valid token is being processed
- When: the system writes the token value to logs
- Then: the token value is not contained in plain text in the server log (hashed or omitted)

## Dependencies

- **Prerequisites**: The person must exist in the system (person creation, no separate UC so far)
- **Downstream effects**: REQ-022, REQ-023, REQ-024 (enrollment flows require a valid token); REQ-025 (audit log)
- **Conflicts**: none known

## Risks of Non-Fulfillment

- Risk 1: Without single use of tokens, intercepted invitation links could be abused to register other people's credentials – severe
- Risk 2: Without an expiry time, links remain valid permanently, increasing the attack surface – medium

## Trade-offs

- None: single use and expiry time of tokens are not optional

## Implementation Notes

- Token value: cryptographically random, ≥ 128 bits of entropy (e.g., 32 bytes Base64url-encoded)
- Expiry time: configurable, recommended 24–72 h; default value as instance configuration
- Token in the DB: store as a cryptographic hash (e.g., SHA-256), not in plain text
- URL fragment handover prevents server log exposure; the enrollment UI must read the fragment on the client side and submit it to the backend via HTTPS POST

## Notes

**Rejected 2026-06-25**: The enrollment token approach was rejected. Enrollment tokens require a secure delivery channel (email or similar) and add unnecessary infrastructure complexity. The chosen alternative is just-in-time enrollment as a required action on first login (UC-03 v0.2.0): the user logs in with the initial password set by the administrator; if a 2nd factor is missing and 2FA is enforced, they are redirected inline to setup – without a separate link. This is the industry standard (Keycloak, Authentik, AWS IAM).

Initial draft from UC-03 v0.1.0, Basic Flow steps 1–3.
