# REQ-196: Multilingual User Manual per Release

## Statement

Every release of OEA **MUST** come with a published user manual in English and German that describes every function of the release – introduction, setup and first steps, administration, usage and the API – with screenshots generated from that release.

## Rationale

Operators (SH-06) have to install and run OEA without reading the source code or the archived changes; architects and analysts (SH-01, SH-03, SH-08) have to learn the functions without a trainer. A manual written only before the release reconstructs behavior after the fact and drifts from the software; a manual that is generated and checked per release stays correct. German is the working language of the first user organizations, English the language of the open-source community (owner request of 2026-10-23).

## Context

The decision on tooling, structure and publication is [ADR-045](../../adrs/ADR-045-user-manual.md): VitePress on GitHub Pages, English source with German translation, screenshots from walkthrough tests against the real stack, versions per release. Contributor documentation (`docs/`, ADRs, specs) is not part of the manual. The referenced use cases are those of the first release: setup and first steps (UC-01, UC-02, UC-03), administration (UC-04, UC-23) and usage (UC-06); every later use case adds its chapter to the manual.

## Type-Specific Fields

### For type=non-functional

**Category**: usability, maintainability

**Measurable target values**:

| Metric | Target Value | Threshold (warning) | Threshold (critical) | Scope |
|---|---|---|---|---|
| Implemented screens covered by a manual page | 100 % | – | < 100 % fails the build | every screen with status `implemented` in `docs/screens/SCREENS.md` |
| User stories `in-progress` or `realized` covered by a manual page | 100 % | – | < 100 % fails the build | all user stories |
| Manual pages present in both languages | 100 % | – | < 100 % fails the build | all pages of `manual/` |
| Implemented API operations in the API reference | 100 %, and 0 planned operations | – | any deviation fails the build | `api/openapi.yaml` of the release |
| Screenshots generated by the walkthrough tests of the release | 100 % | – | any hand-made or missing screenshot fails the build | all images referenced by the manual |
| Manual of a release published after the version tag | ≤ 1 hour | – | not published | each release |

## Acceptance Criteria

**AC1** (structure in two languages):

- Given: the manual of a release
- When: an operator opens the published site
- Then: the English root and the German locale `/de/` each contain the chapters Introduction, Setup and first steps, Administration, Usage and API reference with the same pages

**AC2** (every function covered):

- Given: a screen with status `implemented` or a user story with status `in-progress` or `realized` that no manual page covers in both languages
- When: CI runs
- Then: the build fails and names the missing screen or story and the language

**AC3** (API reference from the contract):

- Given: `api/openapi.yaml` with implemented and planned operations
- When: the manual is built
- Then: the API reference lists every implemented operation with parameters, responses, problem types and required permissions, and no planned operation

**AC4** (screenshots from the release):

- Given: a version tag
- When: the release workflow runs
- Then: the walkthrough tests run against the stack of that tag, produce every screenshot the manual references, and the build fails if a referenced screenshot was not produced

**AC5** (language of screenshots):

- Given: the user interface offers only English
- When: the German manual is built
- Then: it shows the English screenshots; once the user interface offers German, the German manual shows German screenshots without changes to the manual pages

**AC6** (versions):

- Given: the releases v0.1 and v0.2 are published
- When: a reader opens the site root
- Then: it shows the manual of v0.2, the version selector offers v0.1 and v0.2, and `/v0.1/` still shows the unchanged manual of v0.1

## Verification Method

- [x] Method: test (automated) and inspection of the published site per release
- [x] Test setup: coverage check over `docs/screens/SCREENS.md`, `requirements/user-stories/` and the frontmatter of `manual/`; build of the API reference from `api/openapi.yaml`; Playwright walkthrough tests against the Compose stack
- [x] Measuring tool: CI scripts, VitePress build, Playwright
- [x] Pass criterion: all target values met; AC1–AC6 green
- [x] Integrated in CI: yes (coverage check on every pull request, walkthrough tests and publication on every version tag)

## Dependencies

- **Prerequisites**: marking of planned contract operations (retrospective action A1) for AC3; walkthrough test environment with seed data for AC4
- **Follow-on effects**: localized screenshots once the frontend implements ADR-025 (AC5)
- **Conflicts**: none

## Risks of Non-Fulfillment

- Operators cannot install or run a release without support; adoption of the open-source edition stalls (high)
- Functions are used wrongly because only the code describes them (medium)

## Trade-offs

- vs. development speed: every user-visible change also updates two languages and the walkthrough tests

## Implementation Notes

- The manual grows with each change; the definition of done of user-visible changes includes the manual (ADR-045 rule 8)
- The coverage check can run on every pull request; the walkthrough tests and publication are expensive and run per version tag
