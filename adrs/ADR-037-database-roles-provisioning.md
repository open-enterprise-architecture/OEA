# ADR-037: Database Roles and Provisioning

**Status**: accepted
**Date**: 2026-10-13
**Deciders**: [Lukas Mathis – Repository Owner](../MAINTAINERS.md)
**Consulted**: business engineer (data model alignment), solution architect
**Informed**: all contributors
**Partially supersedes**: [ADR-033](./ADR-033-audit-trail-hardening.md) (§1: role name `oea_reporting`, ownership of the reporting schema by `oea_owner`), [ADR-034](./ADR-034-secured-raw-analytics.md) (§2: roles and grants created by Flyway; §3: per-metatype views "regenerated by the backend under `oea_reporting_owner`")

## Context and Problem

ADR-033 (audit trail hardening) and ADR-034 (secured raw analytics) were written in parallel and both define PostgreSQL roles. Aligning the data model with them revealed five contradictions:

1. ADR-033 names the analytics role `oea_reporting`; ADR-034 names it `oea_analytics` and adds `oea_reporting_owner`.
2. ADR-033 lets `oea_owner` own the reporting schema; ADR-034 lets `oea_reporting_owner` own it.
3. ADR-034 lets Flyway (under the migration owner) create roles and grants; ADR-033 requires that roles are created once by a provisioning step with superuser rights and that no OEA role has `CREATEROLE` or is a member of another OEA role.
4. ADR-034 lets the backend regenerate the per-metatype reporting views "under `oea_reporting_owner`", but that role cannot be used by the running application without role membership, which ADR-033 forbids.
5. ADR-034 stores the HMAC key for the analytics request context in `reporting_ctx.keys` inside the database; REQ-188 requires keys outside the database and outside backups.

Nothing is implemented yet; the decision only removes the contradictions.

## Decision Drivers

- One consistent role model for audit, reporting and application (least privilege, ADR-032/033/034)
- No OEA role can create roles or escalate via membership (ADR-033)
- The running application never holds owner rights on audit or reporting objects
- Simple operation with the shipped Docker Compose setup (REQ-075) and with operator-managed PostgreSQL

## Considered Options

### Option 1: Flyway creates roles (ADR-034 as written)

- **Pro**: everything in one migration tool
- **Con**: the migration role needs `CREATEROLE`, which can create a superuser-equivalent chain of roles; contradicts ADR-033

### Option 2: Provisioning step creates roles; separate owners per schema; definer functions for runtime maintenance

- **Pro**: no OEA role can create roles; owners are separated per schema; the application gets only narrow, reviewable entry points
- **Con**: one more setup step and one more set of credentials for the migration step

### Option 3: A single owner role for all schemas

- **Pro**: simplest
- **Con**: whoever can migrate the reporting views can also change the audit schema; weakens ADR-033

## Decision

We choose **Option 2**.

### 1. Roles (final names)

| Role | Login | Used by | Owns |
|---|---|---|---|
| `oea_owner` | yes | migration step: `db/migration`, `db/migration-audit` | schemas `public`, `audit` and their objects |
| `oea_reporting_owner` | yes | migration step: `db/migration-reporting` | schemas `reporting`, `reporting_ctx` and their objects |
| `oea_app` | yes | application runtime | nothing |
| `oea_audit_cleanup` | yes | retention job | nothing |
| `oea_auditor` | yes | verification command, optional external auditors | nothing |
| `oea_analytics` | yes | raw analytics connection pool | nothing |

`oea_reporting` (ADR-033) is renamed to `oea_analytics`. No role is `SUPERUSER`, `CREATEROLE`, `CREATEDB` or `BYPASSRLS`; no OEA role is a member of another OEA role.

### 2. Provisioning step

A one-time provisioning step with database superuser rights creates the six roles, the schemas with their owners and the database-level grants – automatically by the PostgreSQL init script in the shipped Compose setup and by a documented SQL script for operator-managed PostgreSQL. Role passwords are deployment secrets (REQ-188, ADR-036); the Compose file has no defaults.

### 3. Migration step

The one-shot migration step (`oea migrate`, ADR-033 §2) runs Flyway three times with separate history tables: `db/migration` and `db/migration-audit` as `oea_owner`, `db/migration-reporting` as `oea_reporting_owner`. Object-level grants (e.g. `SELECT` of `oea_reporting_owner` on the base tables the views read, `EXECUTE` for `oea_app`) are part of these migrations; role creation is not.

### 4. Regenerating per-metatype views

`reporting.refresh_metatype_views()` is a `SECURITY DEFINER` function owned by `oea_reporting_owner`. It reads the metamodel tables, validates every identifier (`quote_ident`, reserved names, the stable SQL column names of ADR-034 DM-6) and recreates the generated views. It accepts no SQL text and no identifiers from the caller. `oea_app` has `EXECUTE` on this function only and calls it after a metamodel change; the call is audited. `REVOKE ALL ON FUNCTION … FROM PUBLIC` is part of the migration.

### 5. Analytics context key

The HMAC key for the analytics request context stays in `reporting_ctx.keys`, readable only by `oea_reporting_owner` through the definer function `reporting_ctx.current_context()`. This is a documented **exception to REQ-188**: the key does not protect data at rest, it only prevents an analyst from changing their own masking context within a query; anyone who obtains a backup already has the data the key would protect. The key is rotated at least every 90 days and on every suspected compromise; old keys stay valid only for in-flight transactions.

### 6. Smaller clarifications (owner decision Q23)

- **Audit retention**: an increase of the retention takes effect immediately and cancels a pending reduction; a reduction takes effect after 30 days (ADR-033).
- **Analytics request limits**: `maxRows` and `timeoutSeconds` above the instance limit are capped to the limit, not rejected (ADR-034).
- **Problem types**: RFC 9457 problem type URIs follow `urn:oea:problem:<kebab-case-name>`.
- **Anonymization**: anonymizing a person also removes its identity bindings and the link to the EA person entity (REQ-189).
- **Logout**: the API provides a logout operation that ends the current session server-side (REQ-164 AC1).

## Consequences

### Positive Consequences

- One consistent role model across audit, reporting and runtime
- No OEA role can create roles; the running application never owns audit or reporting objects
- Metamodel changes update the reporting views without owner rights in the application

### Negative Consequences / Trade-offs

- The migration step needs two sets of owner credentials
- The analytics context key is in database backups (accepted exception, rotation required)
- A bug in `refresh_metatype_views()` runs with owner rights on the reporting schema; the function must be reviewed like a security boundary

### Follow-up Decisions

- None; implementation details belong to the OpenSpec change that implements analytics
