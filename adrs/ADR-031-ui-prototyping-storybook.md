# ADR-031: UI Prototyping with Clickable Vue Prototypes in Storybook

**Status**: accepted
**Date**: 2026-10-13
**Deciders**: [Lukas Mathis – Repository Owner](../MAINTAINERS.md)
**Consulted**: –
**Informed**: all contributors
**Partially superseded**: 2026-10-15 by [ADR-040](./ADR-040-ui-component-library-after-primevue-license-change.md) — component library Nuxt UI 4 instead of PrimeVue; 2026-10-23 by [ADR-045](./ADR-045-user-manual.md) — GitHub Pages shows the user manual, Storybook moves to `/storybook/`

## Context and Problem

UI mockups were created as Penpot designs generated by scripts (`scripts/penpot/*.js`) and exported as SVG to `docs/screens/`. The flow is one way only: Penpot → SVG. Changes made in the design tool or in code never flow back, so mockups, screen inventory and later implementation drift apart. The SVGs are static and cannot show interaction, states or navigation.

The frontend stack is decided: Vue 3 + TypeScript (ADR-011), PrimeVue + Tailwind CSS (ADR-014), client app and web portal (ADR-008, ADR-009). The API is spec-first (`api/openapi.yaml`, ADR-013).

## Decision Drivers

- **Single source of truth**: a prototype must not be a second artifact that has to be kept in sync with the code
- **Clickable**: prototypes must show navigation, states and interaction, not only static pictures
- **Reuse**: prototypes should become the actual frontend instead of being redrawn
- **Reviewability**: stakeholders without a development setup must be able to look at and click through prototypes
- **Automation**: screen images in the documentation are generated, never maintained by hand
- **Open source**: no proprietary design tool as a prerequisite for contributors

## Considered Options

### Option 1: Keep Penpot (script-generated mockups)

- **Pro**:
  - Already set up; 28 screens exist as SVG
  - Designers can work visually
- **Con**:
  - One-way flow; mockups and code drift apart
  - No interaction; static images
  - Requires a Penpot instance and API credentials

### Option 2: Figma with Dev Mode

- **Pro**:
  - Mature design tool, two-way handoff via Dev Mode
- **Con**:
  - Proprietary and paid; unsuitable as a prerequisite for an AGPL project
  - Still a separate artifact next to the code

### Option 3: Storybook with real Vue/PrimeVue components and a mock API

- **Pro**:
  - Prototypes are the real components: no translation, no drift
  - Stories document every state of a component or screen
  - Clickable flows via the frontend app in prototype mode against a mock API generated from `api/openapi.yaml`
  - Built-in accessibility checks and interaction tests; screenshots can be rendered automatically
  - Publishable as a static site (GitHub Pages) for stakeholder review
- **Con**:
  - Prototyping needs frontend skills
  - Early sketches are slower than in a drawing tool

### Option 4: Histoire with a mock API

- **Pro**:
  - Vite-native and Vue-centric, lighter than Storybook
- **Con**:
  - Smaller ecosystem and less active maintenance; fewer addons (accessibility, interaction tests)

### Option 5: Frontend app with mock API only, no component catalog

- **Pro**:
  - Fewest tools
- **Con**:
  - Individual component and screen states are hard to show in isolation
  - No catalog for review and documentation

## Decision

We choose **Option 3: Storybook with real Vue/PrimeVue components and a mock API**, because prototypes then are the frontend itself and cannot drift from it, and because Storybook offers the largest ecosystem for accessibility checks, interaction tests and automated screenshots.

Concretely:

1. **Storybook** (Vue 3 + Vite) lives in `frontend/`. Every screen in `docs/screens/SCREENS.md` has a screen story: `frontend/src/screens/SCR-NNN-<short-name>.stories.ts`, story title `Screens/SCR-NNN <Name>`.
2. **Clickable flows** run in the frontend app in prototype mode against a **mock API** (Mock Service Worker) whose handlers are generated from `api/openapi.yaml`.
3. **Screen images are generated, never drawn**: a GitHub Actions workflow renders every screen story in light and dark mode with Playwright to `docs/screens/SCR-NNN-light.png` and `SCR-NNN-dark.png`. Screenshots are PNG; SVG export of rendered HTML is not reliable.
4. **Publication**: on every push to `main` that changes `frontend/`, the workflow regenerates the screenshots and commits changed images with `chore(screens): regenerate screenshots`; Storybook is published to GitHub Pages under `/storybook/` (since ADR-045 the site root shows the user manual).
5. **Consistency check**: `scripts/check_screens.py` runs in CI and fails if a screen in `SCREENS.md` lacks its story or image, or if a story or image has no inventory entry.
6. **Penpot is retired**: the Penpot scripts are removed. The existing SVG mockups stay as `legacy-mockup` until the screen story exists; the first generated screenshot replaces the SVG.
7. **Early sketches** (optional): before a story exists, text wireframes (PlantUML Salt) may be embedded in use cases or OpenSpec designs.

## Consequences

### Positive Consequences

- Mockups, screen inventory and implementation share one source
- Stakeholders review clickable prototypes on GitHub Pages
- Screen images in the documentation are always current
- No proprietary tool or design-tool credentials needed

### Negative Consequences / Trade-offs

- UI design work requires Vue/Storybook skills; the UI Designer role writes stories instead of drawing
- Until the frontend exists, only the legacy SVGs are available as screen images
- The screenshot workflow needs write access to `main` (`GITHUB_TOKEN` with `contents: write`) and GitHub Pages enabled

### Follow-up Decisions

- The workflow (`.github/workflows/screens.yml`), Storybook setup and mock API are implemented in the OpenSpec change that sets up `frontend/` (walking skeleton), not ahead of it
- Visual regression testing (comparing screenshots in PRs) is decided once enough screen stories exist

## Notes

Decided together with the switch to OpenSpec-driven implementation: UI prototypes are created in the same OpenSpec change as the screen they belong to.

### Implementation (change us-046-create-catalog, 2026-10-19)

The screenshot workflow `.github/workflows/screens.yml` is implemented with the first screen stories (SCR-020, SCR-028), within the framework of this ADR and with the job split required by [REQ-192](../requirements/req/REQ-192-ci-least-privilege.md) AC2:

- A render job with a read-only token installs the dependencies, builds Storybook and renders the images with `frontend/scripts/render-screens.mjs`; a separate commit job with `contents: write` consumes only the rendered PNGs and changes nothing but `docs/screens/SCR-*.png`
- The image of a screen is rendered from the **first story** of its story file; further stories are variants
- Stories use synthetic data only (`frontend/src/test/catalogs.ts`), injected as a fetch function instead of a mock API server
- Storybook is published by `.github/workflows/pages.yml` together with the user manual, under `/storybook/` of the Pages site (<https://open-enterprise-architecture.github.io/OEA/storybook/>, change `s2c-manual-site`); the repository variable `STORYBOOK_PAGES` of the first implementation is no longer read
- A change that adds a screen story commits the first images itself, rendered with the same script, because `scripts/check_screens.py` checks them before the merge; the workflow then keeps them current
