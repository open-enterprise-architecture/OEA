# Spec Delta

## MODIFIED Requirements

### Requirement: Password login of persons is switched on explicitly

Password login of persons SHALL be off on a newly installed instance. It SHALL be possible only while the operator permits it and the administrators' switch `personPasswordLogin` is on, which is its default. While it is not possible, a password login of a person SHALL fail like a wrong password.

Trace: US-011 AC2, REQ-011, owner decision 2026-10-29

#### Scenario: Fresh instance

- **WHEN** a person with a stored password logs in on an instance where the operator has not switched on password login of persons
- **THEN** the login fails with the generic invalid-credentials answer

#### Scenario: Switched off by an administrator

- **WHEN** the operator permits password login of persons, an administrator switches `personPasswordLogin` off, and a person with a valid password logs in
- **THEN** the login fails with the generic invalid-credentials answer, and switching it on again requires the permission of the operator

### Requirement: Initial password set by an administrator

A principal with `person:manage` SHALL be able to set an initial password for a human person in status `invited` or `active` who has no password, either entered or generated by the system. The password SHALL be stored only as an argon2id hash with the origin `initial` and an expiry (default 72 hours), SHALL never be logged, SHALL be returned once only if it was generated, and the change SHALL be audited as `person.password-set`.

Trace: US-023 AC1, US-023 AC2, US-023 AC4, US-026, REQ-024, REQ-027, REQ-173 AC1, REQ-169

#### Scenario: Initial password set

- **WHEN** an administrator sets an initial password for an invited person
- **THEN** the response carries the expiry but not the password, the database holds only an argon2id hash with origin `initial`, an audit event `person.password-set` exists, and no log line contains the password

#### Scenario: Generated initial password

- **WHEN** an administrator asks for a generated initial password
- **THEN** the response carries the generated password once together with the expiry, and the password satisfies the password policy

#### Scenario: Password already set

- **WHEN** an administrator sets an initial password for a person who already has a password
- **THEN** the request is rejected with 409 and problem type `password-already-set`

### Requirement: Rules for setting an initial password

Setting an initial password SHALL be rejected with 409 if password login of persons is not possible or the person already has a password, with 403 and reason `self-administration` for the caller's own person, with 422 for a service account, and with 422 and problem type `password-policy-violation` for an entered password that does not satisfy the password policy.

Trace: US-023, REQ-024, REQ-028, ADR-032 SoD-1, REQ-169

#### Scenario: Own person and service account

- **WHEN** an administrator sets an initial password for her own person, and for a service account
- **THEN** the first request is rejected with 403 and reason `self-administration`, the second with 422

### Requirement: Changing the own password

A person with a local password SHALL be able to change it with the current password and a new one that satisfies the password policy, including its history. The new password SHALL be stored with origin `self-set` and no expiry, SHALL lift the restriction of the session, and SHALL be audited as `auth.password-changed`.

Trace: REQ-173 AC2, REQ-024, REQ-028, REQ-169

#### Scenario: Password changed

- **WHEN** the person changes the password with the initial password as current password and a new password
- **THEN** further requests of the session are processed, a new login with the initial password fails, a login with the new password succeeds, and an audit event `auth.password-changed` exists
