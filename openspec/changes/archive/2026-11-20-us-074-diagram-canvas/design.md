# Design

## Context

- **Diagrams so far:** change 10 created the table `diagrams` (V46), `core.diagram.DiagramStore`, `app.diagram.Diagrams`, the operations under `/diagrams`, and `DiagramsPage.vue` and `DiagramPage.vue`. The diagram page shows only name, description and viewpoint.
- **Sizes:** the viewpoint returns `effectiveMappings` with the effective default sizes in pt (change 9); `getViewpoint` is readable with `entity:read`.
- **Writing entities:** entities are written through `app.entity.EntityBatch` (validation by `EntityValidator`, write and audit by `EntityWriter`, property write access by `PropertyWriteAccess`). `EntityBatch` runs every write in a transaction of its own (`PROPAGATION_REQUIRES_NEW`). `createEntity` is planned. The column `entities.id` is `SERIAL` (`INTEGER`).
- **Mandatory properties:** an entity of a metatype with a mandatory property that has no default value cannot be created with a name only through the normal write (`MANDATORY_MISSING`, spec `repository/entity-write`). The owner decided on 2026-11-20 that the canvas creates it anyway, marked as incomplete.
- **Deleting entities:** there is no `deleteEntity` yet, but entities are soft-deleted today by the go-live of a solution (retiring) and by the hierarchy (`EntityDeletion`); restoring a deleted entity follows in change 14.
- **Package dependencies:** `app.metamodel` (`Viewpoints`, `PackageImporter`) depends on `app.diagram`, and `app.entity` depends on `app.metamodel`. `CycleRules` forbids package cycles.
- **Finding entities:** no implemented operation searches entities by name across metatypes: `listBrowserItems` lists the root level without a name filter, `queryCatalog` needs a catalog, `listEntities`/`createEntity` are planned.
- **Request size:** the request size filter allows 1 MB by default, with exact-path exceptions for the batch and the package import.
- **The planned read:** `getDiagramView` (`/views/diagrams/{id}`) returns the schema `DiagramView`, which is old and unused; the planned `getPortalDiagramView` references it too.
- **Canvas library:** ADR-007 chose Vue Flow; it is not installed yet.

## Goals / Non-Goals

**Goals:**

- Reading and saving the layout atomically, with new entities.
- Searching the entities a diagram may show.
- The canvas with palette, existing entities, move, resize and remove, "Save" and the read-only mode.

**Non-Goals:**

- Connections.
- Deleting entities, restoring deleted entities.
- Changing the viewpoint, and marking shapes as conflicts.
- Notation shapes.
- Collaboration.
- Entering property values for new entities on the canvas.

## Architecture Constraints

- **ADR-051:** SQL only in `core`. The entity creation reuses the entity write of `app.entity` (no new SQL for entities). No package cycle (D3).
- **ADR-032:** `entity:read` for the view and the search, `entity:write` for the save. Creating entities applies the conditions of an entity write (property visibility; scoping connections do not occur without connections).
- **ADR-033:** `diagram.layout-saved`, and an `entity.created` for each new entity, identical to a batch create.
- **ADR-019:** shapes of a soft-deleted entity are hidden, not removed.
- **ADR-043:** the licenses of Vue Flow (MIT) are allowed; `THIRD-PARTY-LICENSES.md` is regenerated.
- **ADR-013:** the contract first.

## Decisions

### D1 Table `diagram_shapes`

```sql
CREATE TABLE diagram_shapes (
    id         UUID          PRIMARY KEY,           -- client-generated shape ID, stable across saves
    diagram_id UUID          NOT NULL REFERENCES diagrams (id) ON DELETE CASCADE,
    entity_id  INTEGER       NOT NULL REFERENCES entities (id),
    x_pt       NUMERIC(9,2)  NOT NULL CHECK (x_pt BETWEEN -100000 AND 100000),
    y_pt       NUMERIC(9,2)  NOT NULL CHECK (y_pt BETWEEN -100000 AND 100000),
    width_pt   NUMERIC(6,2)  NOT NULL CHECK (width_pt BETWEEN 1 AND 2000),
    height_pt  NUMERIC(6,2)  NOT NULL CHECK (height_pt BETWEEN 1 AND 2000),
    z_order    INTEGER       NOT NULL CHECK (z_order >= 0)
);
CREATE INDEX diagram_shapes_diagram ON diagram_shapes (diagram_id);
CREATE INDEX diagram_shapes_entity ON diagram_shapes (entity_id);

REVOKE ALL ON diagram_shapes FROM PUBLIC;
GRANT SELECT, INSERT, UPDATE, DELETE ON diagram_shapes TO oea_app;
```

- Migration `V47__diagram_shapes.sql`. `entity_id` is `INTEGER` like `entities.id`; the foreign key has no cascade, since entities are never removed for good in v1.0 (ADR-019).
- Shape IDs are generated by the client (UUID), so that comment threads and edges can anchor to them later. On save the stored set is replaced: deleted, updated and inserted by ID.
- A shape ID of another diagram is rejected with 422.
- Coordinates and sizes are in pt with at most two decimals; the client converts pt ↔ px (1 pt = 4/3 px) and rounds to two decimals. A value with more decimals is rejected with 400.
- The drawing order is the order of `shapes` in the save request; `z_order` stores the index.

### D2 Contract

- **`getDiagramView`** (implemented, `entity:read`) returns `DiagramView`, which replaces the old unused schema:
  - `diagram` (`Diagram` of change 10, with the version);
  - `viewpoint`: the `ViewpointConfig` of the diagram's viewpoint (allowed metatypes with names and abbreviations, `effectiveMappings` with sizes and visual hints);
  - `shapes`, in drawing order: `DiagramShape` items with `id`, `entity` (`id` integer, `name`, `metatypeId`), `x`, `y`, `width` and `height`.

  Shapes of deleted entities are left out. The `ETag` is the diagram version. 404 for an unknown or deleted diagram.
- **`saveDiagramView`** (`PUT /views/diagrams/{id}`, `entity:write`, `If-Match` required) takes `DiagramViewWrite`:
  - `shapes` (`maxItems` 2000), in drawing order: `id` (uuid), and exactly one of `entityId` (integer ≥ 1, an existing entity) or `newEntityKey` (uuid, the `key` of an item of `newEntities`), with `x`, `y` (−100 000 to 100 000), `width` and `height` (1 to 2000);
  - `newEntities` (`maxItems` 500): `key` (uuid), `metatypeId` (uuid) and `name` (`maxLength` 255, as an entity name).

  It answers 200 with the new `DiagramView` and `ETag`, or 400 (schema, limits, more than two decimals), 403, 404, 412, 413, 422 and 428. The 422 is the problem type `urn:oea:problem:validation-failed` with `invalidFields` (e.g. `shapes[3]`, `newEntities[1].name`) and `errors` (`ValidationError` with `field`, `code` and `message`, the codes of the entity write such as `MANDATORY_MISSING`), so that the editor can mark the shapes and show the reason.
- **`searchDiagramEntities`** (`GET /views/diagrams/{id}/entities`, `entity:read`): one page of the element entities that are not deleted and whose metatype the diagram's viewpoint allows, ordered by name ignoring case, then ID; `q` (`maxLength` 255) filters by name, contained and ignoring case, wildcards matched literally; optional `metatypeId` narrows to one allowed metatype; `PageParam` and `PageSizeParam` (1–200). Items: `id`, `name`, `metatype` (`MetatypeSummary`); envelope `items` and `page`. 400 for limits, 404 for an unknown or deleted diagram, 422 naming `metatypeId` for a metatype the viewpoint does not allow. Read only, not audited. This is the read of "Add existing"; no existing operation can search entities by name across metatypes.
- **Conventions:** every request string has `maxLength`, the IDs use `UuidIdParam`, the page envelope is named `items`. The planned `getPortalDiagramView` keeps its reference to `DiagramView` (the portal view SCR-052 follows later). The descriptions of `Diagram` and of the tag no longer call the view planned.
- The `x-oea-status: planned` of `getDiagramView` is removed.

### D3 Package and entity creation

- **No cycle:** the view, the save and the search live in a new package `io.oea.app.diagramview`. It depends on `app.diagram` (the diagram, its lock and version), `app.metamodel` (`Viewpoints.get`) and `app.entity` (the entity creation); nothing in `app` depends on it. `app.diagram` stays free of `app.metamodel` and `app.entity`. The controller lives in `api.diagram` or a new `api.diagramview`. `CycleArchitectureTests` stays green.
- **Shape SQL:** `core.diagram.DiagramShapeStore` (read with the entity name and metatype joined, replace, ID ownership check). The search SQL goes into `core.entity.EntityStore` (or a new store in `core.entity`), with typed arguments and the `LIKE` escaping of `listDiagrams`.
- **Entity creation in the caller's transaction:** `EntityBatch` writes in transactions of its own (`REQUIRES_NEW`), so calling `write` would commit the new entities even when the save fails afterwards. `app.entity` gets one public method for creating entities inside the current transaction (propagation `MANDATORY`), e.g. `EntityBatch.createInTransaction(principal, List<EntityInput>, agent)`. It reuses the same steps as an atomic batch create – `PropertyWriteAccess.require`, `MetatypeRules`, `EntityValidator.check` with `Necessity.WARN` for the new entities of the canvas (as the restore does), so that a missing mandatory value is a warning `MANDATORY_MISSING`, not an error, `EntityWriter.write` with one batch ID – and throws `AtomicBatchFailedException` with the issues of all faulty items (paths `entities[i]…`). `app.diagramview` maps the paths to `newEntities[i]…`. No second validation or audit code exists.
- **Required properties (owner decision 2026-11-20):** a new entity has a name and a metatype only. A missing mandatory value is a warning, so the entity is created incomplete; property defaults of the mappings apply as on every create.
- **Incompleteness** is computed, not stored: an entity is incomplete while a mandatory mapping of its current metatype has no value. The view returns per shape `missingMandatory` (the names of the mandatory properties without value, also for properties the reader cannot read the value of, since names are metamodel information) and the shape shows "Incomplete: …" as text and an icon. Every other write keeps `Necessity.ENFORCE`. The values are entered in the details panel of change 12 (`us-074-diagram-entity-details`) or through the batch API.
- **Agent headers:** `X-Agent-Id` and `X-Agent-Run` of the save request go into the `entity.created` events as in a batch.

### D4 Save in `app.diagramview`

Within one transaction:

1. Lock the diagram row (`findForUpdate`); 404 when unknown or deleted. Check `If-Match` (428, 412).
2. Validate (all problems are collected, then 422 with `invalidFields` and `errors`):
   - each shape references exactly one of `entityId` or `newEntityKey`; a key names an item of `newEntities`;
   - `newEntities` keys are unique, and every new entity is referenced by at least one shape;
   - shape IDs are unique in the request and not used by another diagram;
   - existing entities exist, are not deleted, and are element entities; for a shape that is new or now shows another entity, the metatype must be allowed by the viewpoint (BR-DG-01). A stored shape that keeps its entity is accepted even if the viewpoint no longer allows its metatype, so that a later change of the viewpoint configuration does not block every save; marking such shapes as conflicts follows with change 15;
   - each new entity's metatype is an element metatype the viewpoint allows.
3. Create the new entities through the entity creation of D3. A failure rolls back everything and answers 422 naming the new entity.
4. Replace the shapes. Stored shapes of deleted entities that the request does not contain are kept: the client never received them, so their removal is not inferred. The limit of 2000 applies to the request; hidden shapes are not counted.
5. Raise the diagram version and set `updated_at`/`updated_by`. Every accepted save raises the version, also without a difference.
6. Audit `diagram.layout-saved` with the diagram ID, `version`, `added`, `changed` (position, size or drawing order differ), `removed` and `entitiesCreated`.

The diagram version is shared with `updateDiagram`: a rename after the canvas was opened makes the save answer 412.

### D5 Request size

The largest valid body – 2000 shapes and 500 new entities with names of 255 characters – is about 0.6 MB in plain text, but more than 1 MB when the names consist of characters that JSON escapes. The request size filter therefore gets a limit `oea.web.request-size.diagram-view` of 2 MB for `PUT /api/v1/views/diagrams/{id}`; the filter learns to match this path by pattern (today it matches exact paths only). Above the limit the answer is 413.

### D6 Canvas (SCR-021)

- **Library:** `@vue-flow/core` and `@vue-flow/node-resizer` (both MIT), added like the other dependencies (`package.json` range, pinned by `package-lock.json`). A custom node component `EntityShape.vue` shows the name, the metatype abbreviation and the visual hint as border color. Zoom buttons and "Fit view" are Nuxt UI buttons on the Vue Flow API.
- **Read-only mode:** no node dragging, resizing or deletion.
- **`DiagramPage.vue`** shows the canvas instead of the notice. It loads `getDiagramView` and keeps the local state:
  - shapes;
  - new entities;
  - a dirty flag.
- **Palette** (only for `entity:write`):
  - it lists the element metatypes the viewpoint allows;
  - dragging one onto the canvas creates a new shape with the effective default size and an inline name input; an empty name removes the shape again.
- **"Add existing"** (only for `entity:write`): a search dialog over `searchDiagramEntities` with a name input (debounced) and "Load more"; it places the chosen entity with the effective default size of its metatype at the visible center.
- **Shapes:**
  - move by drag, resize at the corners;
  - "Remove from diagram" via the context menu and the `Delete` key;
  - keyboard: arrow keys move a selected shape by 1 pt, or 10 pt with Shift (accessibility).
- **Saving:**
  - "Save" sends `saveDiagramView`;
  - on 412 a dialog offers to reload, discarding local changes;
  - on 422 the named shapes are marked with the message of their error.
- **Unsaved changes:** the route-leave guard and `beforeunload` ask before discarding.
- **Navigation:** pan, zoom, "Fit view", and zoom in and out buttons.

## Risks / Trade-offs

- **[Risk]** Large diagrams (2000 shapes) make the save body large.
  - **Mitigation:** a dedicated limit of 2 MB (D5); a test saves 2000 shapes and 500 new entities with names of 255 characters.
- **[Risk]** The entity creation path is shared with the batch API; a subtle difference in audit or checks would diverge.
  - **Mitigation:** one method in `app.entity` built from the same steps (D3), and a test that a new entity from the canvas is identical to one from the batch (audit, version, history).
- **[Trade-off]** Entities created on the canvas may lack mandatory values (owner decision 2026-11-20). They are marked as incomplete on every shape, and every other write still requires the values.
- **[Trade-off]** Last saver wins per diagram, with 412 on a stale version. Merging comes with collaboration (UC-24).
