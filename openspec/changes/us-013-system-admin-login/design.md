# Design

## Context

Changes 1 and 2 delivered the backend with migration step, startup guards, audit hash chain and the local bootstrapping; the system admin account exists but no login, session or authorization exists, and Spring Security is not on the classpath. The contract already declares `x-oea-authorization` for every operation, the permission catalog and the built-in roles, and operations for logout, `/me`, auth providers and IdP group mappings. See proposal.md for scope and the owner decisions of 2026-10-15 (ADR-042, backend-for-frontend, providers via API, administration without UI, roles only through IdP group mappings).

## Goals / Non-Goals

**Goals:**

- Session and authorization infrastructure that change 3b (OIDC login) and all later operations reuse unchanged
- No principal other than the system admin can gain access while the admin lacks a second factor (ADR-042)
- Enforcement generated from the contract, so that a new operation cannot be added without a permission check

**Non-Goals:**

- OIDC login, IdP-derived roles, refresh tokens and Electron bearer tokens (change 3b and later)
- Administration UI, local role assignments, passkeys, recovery codes

## Architecture Constraints

- ADR-028: controllers in `io.oea.api` implement the generated interfaces; login, enrollment and administration services with transaction boundaries in `io.oea.app`; entities and rules in `io.oea.core`; filters and security configuration in `io.oea.config`
- ADR-032 §8: L1 authentication with allowlist, L2 permissions from `x-oea-authorization`, `denyAll` default, generated matrix test; permissions never embedded in sessions, resolved per request with at most 60 s cache
- ADR-033: every security event is an audit record of the hash chain (new event types in `docs/audit-event-catalog.md`)
- ADR-036 §6: issuer rules G2/G3 apply when a provider is saved outside `dev`; G4 covers the key-encryption key
- ADR-042: setup phase rules
- REQ-165/REQ-187: cookie attributes, timeouts, CSRF, security headers; REQ-168 throttling values; REQ-169 argon2id; REQ-170 TOTP replay; REQ-172 fresh authentication within 5 minutes; REQ-188 encryption

## Decisions

### D1 – Spring Security with an own session filter

`spring-boot-starter-security` provides the filter chain, security headers and the method of rejecting requests; Spring's `HttpSession` is disabled (`SessionCreationPolicy.STATELESS`). An `OeaSessionFilter` in `io.oea.config.security` reads the cookie `__Host-OEA_SESSION`, looks up the session by the SHA-256 of the cookie value, checks revocation, idle timeout and absolute lifetime, updates `last_activity_at` (at most once per minute) and sets an `OeaPrincipal` (principal type, account or person ID, session ID, second-factor flag, `authenticated_at`). The cookie value is 32 random bytes (Base64url); only its hash is stored.

- *Alternative*: Spring Session JDBC (rejected: its schema and attribute serialization do not match the modeled `sessions` table and the audit needs).

### D2 – CSRF and origin checks

State-changing requests with the session cookie need the header `X-CSRF-Token` matching a per-session token (stored as hash; returned by `GET /me` and by the login response) and an `Origin` header that equals the own origin or one of `oea.security.cors.allowed-origins`; `POST /auth/local/login` (no session yet) is protected by the origin check only. Mismatches: 403. CORS is configured only for the allowed origins, never `*` with credentials.

### D3 – Function-level authorization generated from the contract

The build copies `api/openapi.yaml` into the jar (`classpath:openapi/openapi.yaml`). At startup `ContractAuthorizationRules` parses it (Jackson YAML) into `operationId → rule` (`public`, `authenticated`, `permissions`, `anyOfPermissions`; `conditions` are rejected at startup until the first operation needs them). A `HandlerInterceptor` resolves the handler method of the generated interface (method name = `operationId`) and evaluates the rule against the principal's effective permissions before the controller runs. A handler without rule → 403 for everybody; unknown paths → 401 without session, 404 with session. L1 uses the same rules: `public` operations are reachable without session, everything else requires one (401). The matrix test enumerates all handler methods and calls each with a principal without permissions.

- *Alternative*: annotations generated by a custom OpenAPI template (rejected: a second template set to maintain; the runtime parse uses the same contract file the generator uses).

### D4 – Effective permissions

`PermissionResolver` in `io.oea.app` returns the permission set of a principal: the system admin account holds the permissions of the built-in role `system-admin` read from `role_permissions`; persons (change 3b) will add IdP-derived roles. Cached per principal for 60 s and evicted on changes of roles or mappings (ADR-032 §7).

### D5 – Login transaction and second factor

`POST /auth/local/login` takes `loginName` and `password`. During the setup phase a correct password creates the session (`201`, cookie, `csrfToken`). After the setup phase a correct password returns `401` with problem `second-factor-required` and an opaque `loginTransaction` (stored hashed in `login_transactions`, valid 5 minutes, at most 5 wrong codes); `POST /auth/local/login/totp` with `loginTransaction` and `code` creates a second-factor-verified session. Wrong login name and wrong password return the same `401 invalid-credentials`; for unknown names a dummy argon2id verification keeps the timing equal. A successful login with outdated hash parameters rehashes the password (REQ-169).

### D6 – Throttling stored in the database

`auth_throttle` rows per key (`account:<login name>`, `address:<ip>`) count failures in sliding windows; backoff `2^(n-5)` seconds from the sixth failure, capped at a 15-minute temporary lock; the address limit is 100 failures per 10 minutes. Stored in PostgreSQL so that several backend instances share the counters. Throttled requests return the same `401 invalid-credentials` plus `Retry-After`; the first throttling of a key writes `auth.throttled`.

### D7 – TOTP

RFC 6238 with SHA-1, 6 digits, 30 s, accepted window ±1 step; 20-byte secret. Enrollment: `POST /me/second-factors/totp` (requires `authenticated_at` within 5 minutes, otherwise `401 reauthentication-required`) creates a `pending` credential and returns the `otpauth://` URI and the Base32 secret once; `POST /me/second-factors/totp/{credentialId}/confirm` with a valid code activates it and marks the session second-factor-verified. `last_used_time_step` per credential rejects replays (REQ-170). A pending credential expires after 10 minutes.

### D8 – Key-encryption keys and secret encryption

`oea.security.kek.current` (path of a file with a Base64-encoded 256-bit key) and optional `oea.security.kek.previous` (list of paths). Key ID = first 16 hex digits of SHA-256 of the key. Values are stored as Base64 of `nonce (12 bytes) || ciphertext || tag (16 bytes)` with AES-256-GCM; the additional authenticated data binds table, column and row ID so that ciphertexts cannot be swapped between rows. `oea secrets reencrypt` (mode like `oea migrate`, runtime credentials) re-encrypts every value whose key ID is not the current one. Compose: the key file is a Compose secret (`/run/secrets/oea_kek`); development uses `dev/secrets/oea-kek-dev-only.key`, which is hash-listed and rejected by G4 outside `dev`. Guard G4 checks existence, readability, length and the known-development list.

### D9 – Setup phase

`system_settings.setup_phase_ended_at` and `setup_phase_ended_by_action` (`identity-binding`, `idp-group-mapping`). The services creating an identity binding or an IdP group mapping call `SetupPhase.requireSecondFactorFor(action)` inside their transaction: in the setup phase it requires an active TOTP credential of the acting account and a second-factor-verified session (else `403 second-factor-required`), then ends the phase and appends `system.setup-phase-ended`. The login service reads the phase to decide whether TOTP is required.

### D10 – Administration APIs

- Providers: `type` (`oidc`), `name`, `issuerUrl`, `clientId`, `clientSecret` (write-only, encrypted), `scopes`, `enabled`; responses carry `clientSecretSet`. Outside `dev` the issuer must use `https` and must not be a loopback address (same `LoopbackAddresses` as the startup guards); saving requires fresh authentication (5 minutes). `testAuthProvider` and claim mappings are not implemented in this change; unimplemented operations have no handler and are therefore denied for every principal (D3).
- Persons: `POST /admin/persons` (`name`, optional `email`; status `invited`), `GET /admin/persons`, `GET /admin/persons/{personId}`.
- Identity bindings: `POST /admin/persons/{personId}/identities` (`authProviderId`, `subject`), `GET` list, `DELETE`; `link_method = admin-entered`; `UNIQUE(issuer, subject)` → 409.
- IdP group mappings: as in the contract; `groupIdentifier` must be a UUID (Entra ID object IDs, Authentik and Keycloak group IDs are UUIDs; other formats need a provider-specific rule later); delete is a soft delete (`deleted_at`). The self-administration rule (SoD-1, US-147 AC5) needs the caller's token and follows with change 3b.

### D11 – Frontend

`/login` (login name, password, TOTP step when requested), `/me/second-factor` (QR code from the `otpauth://` URI rendered locally, manual secret, confirmation), logout in the header, profile view from `GET /me`. API calls use `credentials: 'same-origin'` and send `X-CSRF-Token` from `/me` on state-changing requests. The setup page links to `/login` after success.

## Data Model

Changes to `docs/data-model.puml` and `business-objects/` (data model rule of AGENTS.md):

- `sessions`: new columns `token_hash BYTEA UNIQUE NOT NULL` and `csrf_token_hash BYTEA NOT NULL` (the cookie value and the CSRF token are never stored); `client_type` `web`; `auth_method` `local-password` | `local-password-totp`
- `local_credentials.status`: new value `pending` for an enrollment not yet confirmed
- New table `login_transactions` (`token_hash`, `system_admin_account_id`, `created_at`, `expires_at`, `failed_codes`)
- New table `auth_throttle` (`throttle_key`, `failures`, `window_started_at`, `locked_until`)
- `system_settings`: `setup_phase_ended_at`, `setup_phase_ended_by_action`
- `auth_providers`: `client_id`, `client_secret_encrypted`, `client_secret_key_id`, `scopes` (the API already has them; the model gains them)
- Business objects: `session`, `system-settings`, `local-credential`, `auth-provider` (if present) updated accordingly

Planned Flyway migration `db/migration/V3__identity_and_sessions.sql` (owner `oea_owner`): `persons` (without the entity link columns), `person_identities`, `auth_providers`, `permissions`, `authorization_roles`, `role_permissions` (seeded from the contract's permission catalog and built-in roles), `idp_group_mappings`, `sessions`, `totp_credentials`, `login_transactions`, `auth_throttle`, the new `system_settings` columns, grants for `oea_app` (no DELETE on persons, identities history-relevant tables except `person_identities` unbinding and the transient tables). A test compares the seeded catalog with `x-oea-permissions` and `x-oea-builtin-roles` of the contract.

## API

Delta to `api/openapi.yaml`:

- Security scheme `cookieAuth`: cookie name `__Host-OEA_SESSION` (**BREAKING**, no client yet)
- New public operations (allowlist): `localLogin` `POST /auth/local/login`, `localLoginTotp` `POST /auth/local/login/totp`
- New operations (`access: authenticated`): `startTotpEnrollment` `POST /me/second-factors/totp`, `confirmTotpEnrollment` `POST /me/second-factors/totp/{credentialId}/confirm`
- New operations: `createPerson`, `listPersons`, `getPerson` (`person:manage`); `listPersonIdentities`, `createPersonIdentity`, `deletePersonIdentity` (`person:manage`)
- Changed: `AuthProvider` gains `clientSecretSet` and `scopes`; `Me` gains `principalType`, `secondFactorVerified`, `csrfToken`, `permissions`
- New problem types: `invalid-credentials`, `second-factor-required` (with `loginTransaction` when issued by login), `reauthentication-required`, `csrf-rejected`

## Risks / Trade-offs

- [Runtime parsing of the contract diverges from the generated interfaces] → both use the same file in the same build; a test fails if a handler method has no rule or a rule names an unknown operation
- [Password-only admin during the setup phase] → throttling, audit events, operator guidance (ADR-042); the setup phase ends before any other access
- [Throttling in the database adds writes on failed logins] → only failures and throttled requests write; successful logins reset the account key
- [Key file lost] → TOTP secrets and client secrets become unreadable; documented backup of the key outside the database backup (REQ-188 AC4), re-enrollment as recovery
- [UUID-only group identifiers] → matches all three supported providers; a provider-specific format rule can be added without changing stored data

## Open Questions

- None that change the plan; the IdP RP-initiated logout URL of `logout` stays empty for local sessions
